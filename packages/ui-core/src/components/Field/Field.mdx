# Field

Pairs a label, a control, an optional description and an optional error — and, more importantly,
wires them together so assistive technology can follow the relationship.

Reach for `Field` for **every** form control. Hand-assembling a `<Label htmlFor>` next to an
`<Input id>` inside a `<div className='grid gap-3'>` is how this library ended up with a label
pointing at an id nothing carried, and an error message that was visible but had no
`aria-describedby`. One component, one place for that to be right.

## Installation

```tsx
import { Field, Input } from '@repo/ui-core';
```

`Field` has **no form-library dependency**. It takes plain values, so it works with `useState`, with
nothing at all, or with TanStack Form via [`FormField`](?path=/docs/ui-forms-form-field--docs) in
`@repo/ui-forms`. If you are building a real form, use `FormField` — it resolves the value and
validation state for you and renders this underneath.

## Features

- Generates the `id`, and derives the message region's id from it, so the association cannot drift.
- Always renders its message region, so an error appearing on blur is actually announced.
- Sets `aria-invalid` and `aria-describedby` on the control, and `required`/`aria-required`.
- Handles controls that a native `<label>` cannot name — groups, and non-labelable elements.

## The `control` bag

`children` is a **render function**, not a plain child. It receives the accessibility bindings to
spread onto whatever the control turns out to be:

```tsx
<Field label='Email address' id='email'>
	{(control) => <Input {...control} type='email' />}
</Field>
```

`control` contains `id`, `aria-describedby`, `aria-invalid`, and one of `required` /
`aria-required`. **It deliberately carries no `value` and no `onChange`** — `Field` is
presentational and knows nothing about form state.

> **Why a render function rather than `<Field><Input /></Field>`?** Because the bindings often
> belong on an element _inside_ what you render. A `Slider`'s control is a `<span role='slider'>`
> several levels below `SliderRoot`; cloning a child could only ever reach the outermost element,
> and would silently put `aria-describedby` on a positioning wrapper where it does nothing. A render
> function lets you say exactly where they go.

## Usage

### Supply an `id`

```tsx
<Field label='Email address' id='email'>
	…
</Field>
```

Optional, but do it. Ids then read as `email` and `email-message` in the DOM. Omit it and `Field`
falls back to `React.useId()`, which is correct but produces ids containing guillemets (`«r3»`) —
valid in an attribute, and a syntax error if you ever try `querySelector('#' + id)`.

### Description and error

<Canvas sourceState='none' of={FieldStories.WithDescriptionAndError} />

Both can show at once; the description renders first. Passing `error` is what puts the field into an
invalid state — there is no separate `invalid` prop, because two sources of truth for one fact is
how a control and its field end up disagreeing.

### Required

<Canvas sourceState='none' of={FieldStories.RequiredField} />

Sets the indicator on the label _and_ `required` on the control. Both matter: the `*` is
`aria-hidden`, so the control's own attribute is what actually announces.

## Composition — one example per control family

### Text inputs

```tsx
<Field label='Email address' id='email' error={error}>
	{(control) => <Input {...control} type='email' value={value} onChange={onChange} />}
</Field>
```

### Textarea

<Canvas sourceState='none' of={FieldStories.WithTextarea} />

Identical — `Textarea` accepts the same bag.

### Booleans

<Canvas sourceState='none' of={FieldStories.WithCheckbox} />

```tsx
<Field label='Accept the terms' id='terms' required>
	{(control) => <Checkbox {...control} checked={checked} onCheckedChange={setChecked} />}
</Field>
```

`Switch` works the same way. Note the label sits _above_ the control here, which suits a field with
a description or error. For a checkbox that reads inline beside its text, use
[`CheckboxLabel`](?path=/docs/ui-core-checkbox--docs) directly instead — that is a different layout,
not a worse one.

### Groups

```tsx
<Field label='Notify me about' id='notify' nativeLabel={false} error='Choose at least one.'>
	{(control) => (
		<CheckboxGroup {...control} name='notify' options={options} value={value} onChange={onChange} />
	)}
</Field>
```

`nativeLabel={false}`, because one `<label>` cannot name several controls. The label renders as a
`<span>` and the group is given `aria-labelledby` pointing back at it.

### Slider

<Canvas sourceState='none' of={FieldStories.NonNativeLabel} />

```tsx
<Field label='Budget' id='budget' nativeLabel={false}>
	{(control) => (
		<SliderRoot defaultValue={[40]} max={100}>
			<SliderTrack>
				<SliderRange />
			</SliderTrack>
			<SliderThumb {...control} />
		</SliderRoot>
	)}
</Field>
```

**The bag goes on `SliderThumb`, not `SliderRoot`.** The thumb is the element carrying
`role='slider'`; putting the bindings on the root names a `<div>` nobody can focus.

### Select and date pickers

```tsx
<Field label='Country' id='country'>
	{(control) => (
		<Select {...control} type='single' options={countries} value={value} onValueChange={onChange} />
	)}
</Field>
```

These render a `<button>` trigger. A `<button>` _is_ a labelable element, so `nativeLabel` stays
`true` and `htmlFor` associates normally.

## `nativeLabel` — when to turn it off

| Situation                                          | `nativeLabel`                                           |
| -------------------------------------------------- | ------------------------------------------------------- |
| `Input`, `Textarea`, `Checkbox`, `Switch`, `Radio` | `true` (default)                                        |
| `Select`, `SingleDatePicker`, `DateRangePicker`    | `true` — the trigger is a `<button>`                    |
| `CheckboxGroup`, `RadioGroup`                      | **`false`** — one label cannot name several controls    |
| `Slider`                                           | **`false`** — a `<span role='slider'>` is not labelable |

## Accessibility

<Canvas sourceState='none' of={FieldStories.ErrorAppearsAfterBlur} />

**The message region is always rendered, even when empty**, and `aria-describedby` always points at
it. This is not tidiness — `aria-describedby` is read when focus lands on a control, so an error
appearing on blur has to arrive in a region that already existed. A live region inserted into the
DOM at the same moment as its content is announced unreliably, because assistive technology never
observed the region become live.

For the same reason it is never hidden with `display: none`, which would remove it from the
accessibility tree entirely and reproduce the exact problem. It has zero height and zero margin when
empty instead.

| Concern       | Behaviour                                                                                                     |
| ------------- | ------------------------------------------------------------------------------------------------------------- |
| Naming        | Native `<label htmlFor>` where possible, `aria-labelledby` where not. Never both.                             |
| Errors        | `aria-invalid='true'` on the control, message reachable via `aria-describedby`.                               |
| Announcements | One `aria-live='polite'` region. Polite, not assertive — an assertive region interrupts mid-keystroke.        |
| Required      | Symbol plus visually-hidden text on the label, `required`/`aria-required` on the control. Never colour alone. |

> **A control must not render its own error as well.** If a control ever grows built-in error
> display, do not pass `error` to `Field` _and_ let the control show it — the message would appear
> twice and be announced twice. `Field` owns the error slot.

**This file's stories run axe as a blocking gate** (`a11y: { test: 'error' }`), unlike most of the
library, which is on report-only because of pre-existing violations. A component whose whole purpose
is correct labelling should fail loudly when it isn't.
