# Field message

A description or validation message belonging to one form control.

> **Not exported from `@repo/ui-core`.** [`Field`](?path=/docs/ui-core-field--docs) renders these for
> you from its `description` and `error` props, and `Field` is what you should reach for. This page
> documents the piece rather than offering it — it is here because the state/icon pairing and the
> live-region behaviour are worth understanding when you read the markup `Field` produces.

## Features

- Composes [`Alert`](?path=/docs/ui-core-alert--docs), so field-level and page-level messaging share
  one colour vocabulary instead of drifting into two.
- Four states, each with a distinct icon shape as well as a distinct colour.
- No assertive live region, so it can sit inside `Field`'s polite one without interrupting anyone.

## States

| Variant | Icon | Meaning |
| ------- | ---- | ------- |
| `info` (default) | `info` | A plain description. Not validation — just guidance about the field. |
| `error` | `x-circle` | Something is wrong and the user must fix it. |
| `warning` | `alert-triangle` | Allowed, but worth a second look. |
| `success` | `check-circle` | Confirmed as valid. |

**Every state has its own icon shape, and this is load-bearing rather than decorative.** A reader who
cannot distinguish red from green has only the shape to go on, so `error` and `success` must never
share one (WCAG 1.4.1, Use of Colour). The same reasoning drives the required indicator on
[`Label`](?path=/docs/ui-core-label--docs).

## Relationship to Alert

`FieldMessage` renders an `Alert` and changes three things:

1. **It narrows the variants.** `Alert` also has `default`, which means nothing under a control, and
   `destructive`, which is a second, near-identical red next to `error`. `FieldMessage` exposes only
   the four states above and does not inherit that duplication.
2. **It picks the icon.** `Alert` leaves that to the caller; a field message should not be able to
   pair `error` with a tick.
3. **It drops `role='alert'`.** This is the important one — see below.

`Alert`'s `info` variant was added for this component. Before it, the palette was `success`,
`warning`, `error` and `default`, with no neutral informational state.

## Accessibility

> **`FieldMessage` is deliberately not a live region.** `Alert` sets `role='alert'`, which is
> assertive — it interrupts whatever a screen reader is currently saying. Correct for a page-level
> banner that appears in response to something the user did. Wrong under a text input, where it would
> cut across the user mid-keystroke every time a message rendered or changed.
>
> [`Field`](?path=/docs/ui-core-field--docs) wraps its messages in a single `aria-live='polite'`
> region instead, which announces changes at the next natural pause. Nesting an assertive region
> inside a polite one would override it for that subtree, so `FieldMessage` clears the role.

Two obligations fall on whatever renders a `FieldMessage`:

| Concern | Obligation |
| ------- | ---------- |
| Association | The message must be reachable from the control via `aria-describedby`, or a screen-reader user will never hear it. `Field` does this; hand-rolled markup must too. |
| Wording | The icon is `aria-hidden`, so the text is the only thing assistive technology receives. "Enter a valid email address" works; "Invalid" alongside a red icon does not. |
