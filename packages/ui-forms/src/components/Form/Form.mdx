# Form

Owns the `<form>` element and the form instance every field below it binds to.

Start every form with it.

```tsx
import { z } from 'zod';
import { Form, FormError, SubmitButton, TextField, useForm } from '@repo/ui-forms';

const schema = z.object({
	email: z.string().min(1, 'Email address is required.').email('Enter a valid email address.')
});

const form = useForm({
	defaultValues: { email: '' },
	validators: { onChange: schema, onSubmit: schema },
	onSubmit: async ({ value }) => save(value)
});

<Form form={form} className='grid gap-4'>
	<TextField name='email' label='Email address' required />
	<FormError />
	<SubmitButton>Save</SubmitButton>
</Form>;
```

## What you get for free

| Without `Form`                                                 | With `Form`                                                       |
| -------------------------------------------------------------- | ----------------------------------------------------------------- |
| Forgetting `noValidate` lets the browser block submit silently | Always set, with no prop to turn it off                           |
| A plain `<Button>` in a form does nothing (`type='button'`)    | [`SubmitButton`](?path=/docs/ui-forms-submit-button--docs)        |
| A server failure belonging to no field has nowhere to go       | [`FormError`](?path=/docs/ui-forms-form-error--docs)              |
| A failed submit leaves focus where it was                      | Focus moves to the first invalid control                          |
| Every field takes a `form` prop                                | Fields read it from context — you write the name and nothing else |

## Validation

Put a schema on the form and let it supply every message. Validate on **change as well as submit**:

```tsx
validators: { onChange: schema, onSubmit: schema }
```

> **Why both.** With submit-only validation a message disappears on the next keystroke whether or not
> the value improved, because nothing is re-checking it. Validating on change means a message clears
> only once the value is genuinely valid.

You can still put a validator on one field with its `validators` prop, but a schema for the whole
form is easier to keep honest.

## Reporting failures from your submit handler

Two mechanisms, and which you reach for depends on who the failure belongs to.

```tsx
onSubmit: async ({ value, formApi }) => {
	const response = await save(value);
	if (response.ok) return;

	// Belongs to a field -> bind it to the field. This is the common case.
	if (response.fieldErrors) {
		formApi.setErrorMap({ onSubmit: { fields: response.fieldErrors } });
	}

	// Belongs to nobody -> throw. <FormError /> renders it.
	if (response.formError) throw new Error(response.formError);
};
```

> **Prefer binding to a field.** A message someone can act on belongs next to the thing they need to
> change. `FormError` is for what is genuinely left over — a 500, a 429, an expired session.

You do not need to clear field-bound errors: editing a field clears the server error attached to it.

Anything after a successful `await` in your handler already runs only on success, so closing a dialog
or firing a toast goes there.

## Layout

`Form` ships **no layout of its own** — pass a `className`.

That matters most inside a dialog, where scrolling depends on the content area being a direct child
of a flex column. Make the form that column:

```tsx
<DialogContent>
	<Form form={form} className='flex min-h-0 flex-1 flex-col'>
		<DialogHeader>…</DialogHeader>
		<DialogContentArea>…</DialogContentArea>
		<DialogFooter>
			<SubmitButton>Save</SubmitButton>
		</DialogFooter>
	</Form>
</DialogContent>
```

## Accessibility

- **A failed submission moves focus to the first invalid control**, in document order — restoring
  what the browser did before `noValidate` removed it. It only happens on an explicit submit, never
  while you are typing.
- Where the invalid thing is a group, focus goes to the option holding the group's tab stop.
- Each field's message region is polite. The form-level one is assertive, because by then the user
  has pressed submit and stopped to wait for a result.

## One thing to watch

A field's `name` is a plain string, and nothing checks that it exists — not the compiler, not the
runtime. **A misspelled name renders, accepts input, and silently never submits.**

That is the cost of fields finding their form by context instead of by prop. The alternative would
mean importing field components from a factory rather than from the package, which was judged the
worse trade.
